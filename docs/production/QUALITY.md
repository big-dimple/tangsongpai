# 验收与发布门禁

本文件全部数值为项目目标/初始警戒线，不是当前产品实测成绩，也不是外部标准声称。每次报告必须分别列机器检查、人工操作、视觉批准、真人对标，不能把其中一种替代另外几种。

## 1. 证据等级与文件格式

PASS：实际在明确版本/环境运行并有证据；FAIL：已运行未满足；NOT_RUN：没有运行；BLOCKED：缺环境/输入/批准；N/A：确实不适用且说明理由。计划、代码静态推断、旧提交结果不能填 PASS。

每包证据放 `docs/production/evidence/<task-id>-<date>.json`，大体格式：

```
{
  "taskId": "R00",
  "testedCommit": "实际被测试的40位SHA",
  "rulesVersion": "r1或r2",
  "contentHash": "实际内容哈希",
  "environment": {"os":"实际值","node":"实际值","browser":"实际值","device":"实际型号或not-run"},
  "checks": [{"name":"检查名","command":"实际命令","status":"PASS/FAIL/NOT_RUN","exitCode":0,"evidence":"仓库相对路径或稳定CI链接"}],
  "humanReview": {"status":"NOT_RUN","reviewer":"","evidence":""},
  "limitations": ["没有运行的边界"],
  "nextTask": "实际下一任务"
}
```

PASS 才允许 exitCode=0；人工判断没有命令退出码，不虚构。视频、HAR、trace 可保存为 CI artifact，但要记录固定运行 ID 和保留策略；重要批准金样及简明结果应留在仓库/发布附件，不能只藏 gitignore shots。公开仓库不提交参与者身份、聊天、设备账户或密钥。

`check-production-plan` 只检查任务图/证据指针结构，不验证日志真实执行或品质，它不是审查员。完整质量评审仍需要逐项核对。

## 3. 规则与确定性门禁

G01–G15 全部通过，逐事件与最终分都正确；12牌型、六角色、每种增强/消耗品/长期道具/Boss 有正反和边界用例。至少加入1000个固定生成案例验证实例守恒、非法动作无副作用、序列化往返与重放一致；失败保存 seed/command 序列，不能只输出随机失败一次。

覆盖率仅作提示：核心 reducer/scoring 的分支目标90%，但即使100%也必须有显式结果断言。通过改动顺序、漏扣金币、重复奖励、错用held集合等变异反例检验测试确实能失败。不可把跟实现同一段代码算出来的值当独立 expected。

RNG 独立域验证：增加一次粒子抖动不改变牌堆，打开详情/预览不改变骰子，商店刷新不改变已保存的当前牌堆，恢复后下一随机结果一致。测试机器人的实际行动与UI提交同命令流时 stateHash 完全相同，不要求两种策略行动相同。

## 4. 完整流程与故障注入

E2E 至少包括：六选角入口；买一张/钱不足/满槽/出售替换/调序/付费刷新；选择/取消/弃牌/出牌/查牌组；普通胜利→商店→Boss；次数耗尽失败；最终胜利→无尽/新局；设置与继续；子目录资源路径。

浏览器检查 Chromium、Firefox、WebKit，手机用真实触控事件而非只有 hasTouch 标志。至少两个不同角色脚本化通过全部重要路径，所有角色有领域全局用例。只在测试构建开启可观察性 hook；E2E 可读取状态断言，但不能直接调用私有方法伪装用户点击。

故障表：出牌双击、购买双击、演出中退出/快进、切后台、旋转、页面刷新、存储quota失败、坏存档、内容版本不符、资源404/加载超时、音频启动拒绝、多标签同时写、长局100次场景切换。每项写期望结果与实测，不只笼统说“兼容性良好”。

恢复测试至少在七个检查点刷新：选角确认后、商店首次展示、买入后、刷新后、出牌刚提交、演出中、过关奖励后。金币/牌组/货架/RNG游标/状态哈希一致，不能回档刷同一免费货架或重复领奖。

## 5. 设备与性能目标

R00登记真实支持矩阵，至少桌面Chrome、一台主力Android Chrome、一台iPhone Safari；实际型号/OS/浏览器版本不可省略。可额外测内嵌WebView，但没测过就不宣布支持。模拟器用于自动化，不代替真机触感/音频/内存。

首屏目标：冷缓存10Mbps、RTT80ms的固定测试条件，首次可进行有效操作≤4秒（至少20次，报告中位数与P95），第一交互前实际传输≤4MB。总发布runtime资源初始预算≤20MB；源图/GLB不包括在runtime白名单中。4MB/20MB是预算，不是故意把可读画面压糊的理由。

运行目标：主力设备60FPS方向优化，常规流程95%帧≤20ms、P99≤50ms；选择反馈P95≤80ms；一次典型大连锁不能出现>150ms规则计算长任务。低端设备30FPS可作为兼容底线，但不因此自动算对标通过。测得超标先定位规则、纹理解码、重建对象、过度绘制，再决定优化，不先换引擎。

连续30分钟和100次场景切换检查趋势：监听/tween/音频实例不持续累计；手牌重绘不每次创建整个舞台；有效纹理预算初始96MiB，按解码尺寸估算并结合工具验证。浏览器无法可靠测量某项内存时写测量限制，不能把包体积当显存。DPR上限初始2，可降级；降级不改命中区/文字最低可读尺寸。

## 6. 美术门禁

技术：文件可加载、格式/尺寸/alpha/帧序/crop/hash一致、来源记录齐全、运行时只引用批准版本。视觉：统一语法、角色可区分、字和花色能读、效果不挡操作、稀有度非仅颜色、竖屏不卡切、不出现乱码/多余肢体/水印。两者独立记录。

A01批准必须包含实际牌桌大小、两角色对比、三稀有框和短反馈，而不是一个“整体感觉不错”。A03每小批提供联系表并保留明确验收结果。没有用户或被授权审美评审的确认，Agent不能自行批准自己的作品后继续扩产。

## 7. 平衡与复玩证据

V阶段：24牌/2角色/2章，至少三类可行构筑，不通过测试硬塞指定神牌。基础教学种子保证展示必要机制，而非用教学通过率替代自然局。

B00：至少每角色500个训练seed和独立500个留出seed，三类策略（合法随机、可见信息贪心、有限规划），总计至少18,000完整局；预算不足可先小样本调试，但正式证据不得偷偷缩为10seed。CI常规跑小型固定回归，完整报告可单独批处理。留出集不能看到失败就换seed，发现缺陷修复后应标注重用并建立新留出集。

策略必须决策商店/出售/弃牌/调序，不仅枚举当前手牌。相同seed对比角色采用配对记录，不能把相关样本全当独立样本放大置信度。报告分母、胜率区间、按章死亡、平均剩余次数/金币、购买可见机会、实际使用、构筑转型、失效/无法行动次数。异常seed保留可重放命令日志。

初始诊断警戒线：D0贪心完整通关率20%–65%用于提示难度偏离，不是自动调参目标；同能力策略各角色差异>15个百分点应解释并查样本；某牌在可购时几乎必选且跨角色主导，需要检查是否毁掉取舍。相关性不是强度的因果证明，不按一张使用率图直接削牌。

六大构筑族各应有自然抽样全局可行轨迹，熟练策略应总体优于随机；不能要求每角色都能同样强地玩每族。持续二三十次独立新局只出现同一解法时，不靠再加数值相似的牌解决。

## 8. 对标 Balatro 的人测

V01先8–12名参与者找方向性问题，至少包含未玩过同类的新手和熟悉Balatro的人；用相同任务说明记录问题，不引导受试者称赞新产品。若无人可测，V01保持BLOCKED，不让AI代理玩家宣称好玩。

D21将A01用户Android关键节点放行与此专题分开：用户明确接受对应SHA的视觉/操作/音画后，经A02核对可以继续C00–C04；这不满足本节8–12人要求，也不自动通过iPhone、长局性能或最终对标。V01的缺人不阻止已放行的工程，但L00增加V01前置。D22已记录用户实际核验完成与工程放行；条件性意向仍不是批准，未来未获认可的门禁不能自动解除。

B/L阶段至少24人做配对、交叉顺序比较，记录所用Balatro版本/平台与本项目构建；一半先玩A，一半先玩B，避免把熟悉顺序误认为体验优势。比较UX列出的八类任务，区分学习时间与熟练操作时间。参与者数据匿名，公开仓库只存汇总和授权可公开记录。

硬底线：主流程任务成功率≥95%、无不可恢复存档损失/软锁、主操作误触率≤2%；任何可复现关键路径失败都先修，不用平均分盖住。

主观维度使用7分量表：可控、可理解、连锁满足感、构筑选择、再玩意愿。核心维度配对均值/中位数目标均不低于基准，同时报告区间与具体低分原因。若区间仍包含明显劣势（初始检查边界为-0.5分），继续收样本或整改，不能把“没有显著差异”当成“证明持平”。24人是起点，不保证统计上足够。

这些证据只能支持相应版本、设备、任务与样本范围的结论，不能证明所有玩家所有体验永远相同。若用户仍认为某核心维度明显差，必须把具体问题列入整改，不能用数值平均分顶回去。

## 9. 阶段出口

R：领域一致、金样例、完整状态、可恢复/可取消、手机真实布局、CI可运行；没有“全局已平衡”要求，但不得遗留已知算错/误扣/重复发奖。

V：三类构筑与专题真人反馈通过；D21允许A01/A02用户关键放行后先开展内容工程，专题未通过仍不得形成L00正式候选。正式素材量产继续按A01/A03批准范围，不能把工程放行当全部批次获批。

A：金样明确批准，实际runtime接入达清晰/资源预算；之后才批量。

C：范围内全部内容有规则、实现、测试、文案、资产映射和图鉴，不存在死按钮/伪效果。

B：完整留出报告、设备长局、对标差距整改完成；各证据互相可追踪。

L：未关闭P0/P1为0；所有声明支持环境均实测；没有未解决的来源/发布白名单问题；存档升级/回退有效；真实构建哈希、发布说明、回退步骤、已知非阻断问题和用户验收记录齐全。

## 10. 发布后的边界

按用户明确分工，L02由开发Agent交付已签收的仓库/可校验构建，用户自行部署；不代办Cloudflare、准备部署交接材料或开账户/购买云服务。线上冷启动/完整一局/刷新恢复仍是独立证据，由实际操作者提供；没有结果标NOT_RUN，不用本地成功或push成功代替线上验证。不得将“开发交付已完成”写成“线上已通过”，也不把用户负责的部署当成必须代办的开发包。

任务做完后的维护入口仍为plan/handoff；新增问题先建有证据的工作包，不在多个聊天里各自口头安排。新会话能准确区分已实现、已验证、已批准和待验证，才算交接完成。
